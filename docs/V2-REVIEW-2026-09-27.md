# OpenCode v2 integration review — 2026-09-27

Updated 2026-09-28 after the released-only migration and code-review fixes.

## Sources and scope

Compared this Android client and its synthetic fixture with the official [v2 migration guide](https://opencode.ai/v2/docs/migrate-v1/), [client guide](https://opencode.ai/v2/docs/build/client/), [API reference](https://opencode.ai/v2/docs/api/), and [published OpenAPI contract](https://opencode.ai/v2/openapi.json). The API reference describes an experimental HTTP surface; recheck it when updating the server. The app does not aim to provide every CLI, plugin, provider-authentication, or server-administration feature: the primary workflow is connecting to an existing server, browsing sessions, sending prompts/commands, streaming results, and resolving pending input.

## Completed in this review

- Migrated to the released `@opencode/client` 2.0.18. The app uses the documented API exclusively, including `GET /api/info`, rename, clear revert, form discovery/cancel, command, permission reply, and interrupt. Existing Basic authentication and directory scope are retained.
- Reconciled retry, durable history, and revert events; filtered disabled models; preserved form option wire values and optional answers; exposed saved approvals for review/removal when supported; clarified the scope of an **Always** permission.
- Converted the synthetic fixture and its schema/event assertions to the released contract only, with generated-client and app-client end-to-end tests. It now simulates directory browsing, file search/read, saved approvals, and quiet SSE subscriptions. See [development environment](DEVELOPMENT-ENVIRONMENT.md).
- Refreshed Expo SDK 54 patch dependencies, peers, Sentry, and compatible JavaScript packages. `react-native-svg` remains on the existing 15.15.1 pin with an explicit Expo check exclusion pending an intentional native dependency change.
- Removed the unsupported file-roots and server-home shortcuts, plus obsolete beta transport and test-only helpers. The directory browser, recent directories, and absolute path entry remain available. Fixed saved-password connection tests, released-server diagnostics, stale reconnect statuses, revert races, and project-scoped saved approvals.
- The follow-up review fixed wrong-session sends during cold loading, re-entry losing the Stop control, cross-directory pending input disappearing on reconnect, interrupt/completion races, list reordering, async edit/undo draft loss, and stale permission reply rollback. The fixture now emits released tagged errors and canonical idle messages so tests exercise the real reconciliation path.

## Follow-up work requiring design or migration decisions

| Priority | Area | Decision / work needed |
| --- | --- | --- |
| High | Wider released-server coverage | The fixture validates the implemented app surfaces against released schemas and the event manifest, but cannot represent every provider/model, filesystem or prompt scenario. Extend it when a new mobile feature uses those routes; run a disposable real v2 server for contract differences the fixture cannot reproduce. |
| Medium | Queued prompts and session inbox | New `session.inbox` and prompt `delivery` (`steer`/`queue`) allow interactions while execution is in progress. Decide UI semantics for edit/cancel/reorder and whether the composer should default to steering or queuing; model pending optimistic entries and test against the fixture. |
| Medium | Session operations | The v2 API offers fork, compact, context, diff, background, stats, import/export, session view and session shell. Decide which belong in a mobile workflow, then implement corresponding controls and fixture behavior. Current core session create/list/open/delete/rename, prompt, command, interrupt, revert, agent/model selection, and input resolution are covered. |
| Medium | Dynamic forms | Form fields can include conditional `when`, `hidden`, and `default` behavior and richer value types. The current question UI handles the question-tool subset, required/optional fields, options and custom answers. A generalized form renderer needs conditional evaluation and additional input types. |
| Medium | Cross-client events | Consider `location.shutdown`, model/provider changes, session metadata/permissions changes, and usage updates for instant resync instead of waiting for refresh/reconnect. Explicit permission-rejection messages and session prompt delivery IDs could also improve input handling. |
| Low | Home shortcut | `GET /api/location` does not expose the server's home path. Only add `~` navigation if the released API provides a reliable home-discovery mechanism; absolute navigation works today. |

## Verification and limitations

- `bun run typecheck`, `bun run test` (384 pass), `bun run dev:fixture:test` (16 pass), and Android x86_64 debug build passed. The released fixture was driven in the API tests and Android emulator: seeded root/child sessions and transcript, streamed prompt, slash command, interrupt, edit/undo, pending permissions, question forms, saved approvals, and directory navigation all worked with correct counters. Re-entering an active run retained its Stop control; cold switching did not display the prior session transcript.
- A separate scratch OpenCode **2.0.18** server on loopback port 4599 was used to probe released routes and saved approvals. It ran with temporary test data under `/tmp/opencode/`, used no normal user sessions, and was stopped after probing. No service configuration or persistent user files were changed.
- The fixture SSE connection remained open for 12 seconds without events in a separate loopback test (curl reached its own timeout; no server disconnect). Managed fixture and emulator processes were stopped after verification.
- No physical phone, production account, real model response, provider authentication, notification delivery, biometric sensor, or remote TLS connection was validated. These need targeted device/server checks before distribution. Expo doctor still reports environmental/native-project warnings (including unavailable `npm` checks); `expo install --check` and the Android build passed.
- Emulator/Metro logs showed no JavaScript exceptions or native crashes. Nonfatal dev warnings remain for React Navigation's object-form `navigate`, Sentry's disabled-development app-start span, and occasional Android/Metro transport hiccups. The emulator cannot exercise notification delivery because the app requires `Device.isDevice`.
